    CRAWCUS¶

    Contract · Receipt · Attestation · Warrant — an open specification for cryptographic audit receipts covering both application transactions and AI-inference decisions under one canonical shape.

    The specification is authored openly, dual-licensed (CC-BY-4.0 for spec text, Apache-2.0 for code), and on a Linux Foundation AI & Data submission path via the Joint Development Foundation. Any party — systems integrator, adjacent vendor, individual developer, regulator — can implement a conformant runtime or verifier.

    CRAWCUS defines the payload semantics and regulation mapping for cryptographic audit receipts. Envelope-level transparency is the domain of IETF SCITT (RFC 9943, RFC 9942). That covers registration of Signed Statements with a Transparency Service and SCITT receipts (COSE Receipts, RFC 9942). SCITT treats the payload as opaque, and CRAWCUS is designed to be carried as a SCITT payload. The profile is a draft and has not been tested against any Transparency Service: see CRAWCUS and SCITT.

    Why this exists¶

    When a regulator, auditor, or plaintiff asks "prove this record has not been altered since it was written," the honest answer available today is usually one of:

    • "Trust our vendor's audit log." Useless when the vendor is a defendant.
    • "Run our proprietary tool." A black box the regulator cannot independently verify.
    • "Here are our SIEM logs." Unsigned and mutable by anyone with SIEM admin.
    • "We put hashes on a blockchain." GDPR-incompatible at enterprise write throughput.

    CRAWCUS makes a fourth answer possible: replay the receipt chain against any conformant verifier and check its integrity cryptographically. Hash-chain integrity is verifiable today; verifying who signed a chain (signer trust) is still in progress — see crawcus#1.

    What CRAWCUS is¶

    Every CRAWCUS receipt is a small structured JSON document, canonicalised per RFC 8785 (JCS), hashed with SHA-256, and appended to a hash-chained log where each entry references the hash of the previous one. Tampering with any historical record breaks the chain in a way any auditor can verify with an open-source tool in seconds.

    CRAWCUS composes existing open standards. The primitives underneath — canonical JSON, SHA-256, timestamp formats, signature envelopes — are unchanged. The value CRAWCUS adds is the shape: a specific set of fields, their meanings, and two-scope coverage of both application transactions and AI-inference decisions under one canonical form.

    Conformance tiers¶

    Ratified 2026-09-01: CRAWCUS ships as a two-tier spec so implementers can pick the level that matches their integration surface.

    Tier Primitives Sufficient for Reference implementations
    CRAWCUS-Core-1.0 Contract · Receipt · Attestation · Warrant (4) Hash-chained audit interop, CloudEvents / JWT / SD-JWT payload embedding, federated-learning per-node receipts, most application-level audit trails crawcus-flower (Python client for the Flower federated-learning framework)
    CRAWCUS-Extended-1.0 Core + Disclosure · Consent · Lineage · HumanOversight · Tool-use (9) AACI-shape regulator compliance: GDPR Art. 22 automated-decision-making, EU AI Act Art. 14 / Art. 50 human-oversight + deepfake-disclosure, FERPA §99.31 disclosure-consent @crawcus/regulations-gdpr, @crawcus/regulations-ferpa, @crawcus/regulations-eu-ai-act

    Implementers declare their conformance tier in package metadata. Full details: Architecture primitives.

    Reference implementations¶

    The specification ships alongside reference implementations that adopters can point at, extend, or replace with their own conformant runtimes. Reference implementations are one demonstration of correctness — never "the" reference. Anything passing the @crawcus/tck fixture set at the appropriate conformance tier is by definition CRAWCUS-conformant.

    @crawcus/regulations-ferpa §99.31 factories + §99.7 annual-notice template. @crawcus/core, @crawcus/tck
    @crawcus/regulations-eu-ai-act Art. 14 (human oversight) + Art. 50 (deepfake / synthetic-media disclosure) factories and templates. @crawcus/core, @crawcus/tck

    Regulator or auditor Wire format → verify a real chain end-to-end using the reference verifier

    Engineer building a conformant runtime Wire format → Contract primitive → clone the TCK fixtures, run against your implementation
    Author of an adjacent open-source project (federated learning, model serving, LLM observability, MLOps) Look at clients/flower/ as the pattern — a small client that emits per-node receipts. The same pattern generalises to any framework that surfaces a per-decision or per-call boundary.
    Standards-body reviewer (LF AI & Data / JDF) Governance → Wire format → Architecture primitives

    Standards CRAWCUS builds on¶

    CRAWCUS does not reinvent cryptographic primitives. It composes:

    Primitive Standard
    JSON canonical serialization RFC 8785 JCS
    Chain-link hash FIPS 180-4 SHA-256
    Timestamps RFC 3339 (subset of ISO 8601)
    Optional signature envelope DSSE
    Optional supply-chain signing Sigstore
    Optional transparency envelope SCITT: RFC 9943, RFC 9942. Payload profile in draft
    Erasable-immutable log pattern GDPR crypto-shred + tombstone — not yet specified
    Actor-attribution conventions OAuth 2.0, mTLS, SAML — no CRAWCUS-specific extension

    Governance + licensing¶

    • Governance: authored under the model described in GOVERNANCE.md. Pre-donation phase (2026-09-01–): single maintainer with public Discussion-based decision-making. Post-donation: LF AI & Data / JDF governance.
    • Standards-body track: Linux Foundation submission planned. Rationale: 6–12 month realistic timeline, industry-neutral governance from day one, alignment with peer projects (C2PA, in-toto, Sigstore) in the receipt / supply-chain-signing space.
    • Code licence: Apache-2.0 (with per-package LICENSE files that may declare MIT).
    • Specification licence: CC-BY-4.0.
    • Contribution mechanism: DCO sign-off (git commit -s); no CLA required.
    • Security disclosures: SECURITY.md — private disclosure to paul@tallyseal.org (subject prefix [CRAWCUS SECURITY]) or GitHub Security Advisories.

    Openness — what we claim, what we do not¶

    We are careful with claims. A receipt standard is only as trustworthy as the honesty of its openness claims.

    What is true today:

    • The spec is published and free to implement (CC-BY-4.0).
    • Reference implementations are shipped as open source (Apache-2.0).
    • Every runtime — including the reference implementations — is measured against the same TCK fixture set.
    • Anyone can verify a chain's hash-chain integrity independently of any vendor (signer-trust verification in progress — crawcus#1).

    What is not yet true:

    • Multi-vendor implementation ecosystem — the reference implementations here are the initial implementations. Third-party conformant implementations are actively encouraged.
    • LF / JDF adoption — submission planned, not yet submitted.
    • Widespread production deployment — early adopters welcome.
    • Interop with SCITT Transparency Services. The payload profile is a draft; registration against Transparency Service implementations is planned and not yet tested.

    Verifying releases (planned)¶

    Publishing is planned to use Trusted Publishers (OIDC — no long-lived API tokens) with Sigstore attestations bound to the specific source commit + GitHub Actions workflow run for every @crawcus/* npm package and crawcus-* PyPI package. This pipeline is not in place yet, so there are no attested releases to verify today. Publishing an audit-integrity library without cryptographic supply-chain proof would be self-parodying — which is why this lands before we call any release stable.

    Once it lands, each release will include the exact sigstore verify command in its release notes. See SECURITY.md §"Supply-chain integrity — what the project commits to" for the planned commitment.
